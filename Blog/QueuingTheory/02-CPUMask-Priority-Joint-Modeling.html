CPUMask + Priority Joint Modeling

N-core resource allocation with CPUMask (physical isolation) and preemption priority.

Architecture Parameters (k, m, n)

┌────────────┐  ┌────────────────┐  ┌────────────┐
│ A-Dedicated│  │  Shared (A↑)  │  │ B-Dedicated│
│    k cores │  │    m cores    │  │   n cores  │
│  A only    │  │ A first, B ↑ │  │   B only   │
└────────────┘  └────────────────┘  └────────────┘

Constraint: k + m + n = N

Special Cases:
  (k=N, m=0, n=0) → All to A (B starved)
  (k=0, m=0, n=N) → All to B (A starved)
  (k=0, m=N, n=0) → All shared (pure priority)
  (k=1, m=N-1, n=0) → 1 dedicated + rest shared (recommended)

Gain Decomposition: Architecture vs Scheduling

Key Insight

Priority's advantage comes from TWO sources that must be distinguished:

Total Gain = Architecture Gain + Scheduling Gain

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Architecture Gain (Main Source):
  From merging isolated pools into shared pool

  CPUMask: A uses k cores, B uses (N-k) cores (separate)
  Priority: A uses N cores, B can use ALL cores' idle time

  A's available cores: k → N (increase of N-k cores)
  B's capacity: (N-k)μ → Nμ - λ_A (increase of kμ - λ_A)

  → This is "positive-sum": reclaiming originally wasted resources
  → Independent of scheduling algorithm

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Scheduling Gain (Secondary Source):
  From preemption priority isolating A from B

  A: λ_B doesn't appear in A's formula → A's delay decoupled from B
  B: Still subject to preemption effects (cache pollution)

  → "Interference elimination", not redistribution

Fair Comparison: Same Resource Pool

When comparing with the same c_A = k (same resource pool):

CPUMask (k cores for A):
  Wq_A^iso = ErlangC(k, λ_A/μ) / (kμ - λ_A)

Priority (still k cores for A, but A can preempt B):
  Wq_A^pri = ErlangC(k, λ_A/μ) / (kμ - λ_A)

Conclusion: Wq_A^pri = Wq_A^iso (A's delay is IDENTICAL!)

Priority's advantage for A comes from ARCHITECTURE (more cores),
not from scheduling algorithm.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

For B's capacity (same resource pool comparison):

CPUMask: B capacity = (N-k)μ
Priority: B capacity = (N-k)μ + (kμ - λ_A) = Nμ - λ_A

→ Priority still wins for B (reclaims A's idle capacity)
→ This IS a Pareto improvement: A unchanged, B better

Key Formulas

A's Wait Time (same resource pool, c_A = k)

Wq_A = ErlangC(k, λ_A/μ) / (k·μ - λ_A)

Note: A's delay is the same whether using CPUMask or Priority
      (when compared fairly with same c_A)

B's Effective Capacity

C_B = (N - k)·μ + k·(μ - λ_A/k)  [with k dedicated for A]
     = N·μ - λ_A  [when k dedicated cores idle capacity reclaimed]

Simplified (n=0, m=N-k):
C_B(k) = (N - k)·(μ - λ_A/N) + k·(μ - λ_A/N)
       = N·μ - λ_A - (N-k)·λ_A/N
       ≈ N·μ - λ_A  (when λ_A << Nμ)

Conservation Law

N·μ = λ_A + C_B + C_waste

C_waste = k·μ·(1 - ρ_A,core)
        = k·(μ - λ_A/N)  [idle capacity on A's dedicated cores]

Burst Tolerance Metrics

β_max

Max Burst Multiplier

β_max = C_B/λ_B

H

Headroom

H = C_B - λ_B

T_drain

Recovery Time

T_drain = backlog/H

T_drain = ((λ_burst - C_B) × T_burst) / (C_B - λ_B)

Key Findings

Priority dimension (adjusting m): Architecture gain dominates

More shared cores → more capacity reclaimed from idle → Pareto improvement

CPUMask dimension (adjusting k): Tradeoff EXISTS

More dedicated cores → stronger isolation but C_B ↓ and waste ↑

Recommendations

Best Practice: k=1 (minimum safety net) + Priority

Summary:
  CPUMask buys robustness outside the model (cache isolation, scheduler bugs)
  Priority buys efficiency inside the model (resource sharing)

Decision Framework:
  1. Check system feasibility: λ_A + λ_B < N·μ ?
  2. Calculate k_max = floor(N - λ_B/(μ - λ_A/N))
  3. If scheduler is trusted: k = 0 (pure priority)
  4. If engineering conservatism needed: k = min(1, k_max)
