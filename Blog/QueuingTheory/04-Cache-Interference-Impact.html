Cache Interference Impact on Scheduling

How cache interference changes the Pareto frontier between CPUMask and priority scheduling.

Cache Pollution Mechanism

Problem 1: Cache Cold Start

When A preempts B, A's code/data is not in cache → high L1/L2 miss rate for first few cycles

Problem 2: TLB Flush (Partial)

Address translation cache may need partial refresh → increased memory access latency

Problem 3: Branch Predictor State

B's branch pattern pollutes branch predictor → A's prediction accuracy decreases

Effective Service Rate Model

With cache interference, A's effective service rate on shared cores:

μ_A,eff = μ × (1 - δ)

Where δ is the cache interference factor (0 ≤ δ < 1)

δ = δ_cache + δ_tlb + δ_branch

Component breakdown:
  δ_cache   ≈ 5-15%   (cache cold start losses)
  δ_tlb     ≈ 1-5%    (TLB refill losses)
  δ_branch  ≈ 2-8%    (branch prediction losses)

Typical δ values:
  Light interference (small working set): δ ≈ 5-10%
  Medium interference: δ ≈ 10-20%
  Heavy interference (large working set): δ ≈ 20-35%

Modified Wait Time Formula

Original (ignoring cache interference):
  Wq_A^pri = ErlangC(N, λ_A/μ) / (Nμ - λ_A)

Modified (considering cache interference):
  Wq_A^pri(δ) = ErlangC(N, λ_A/(μ(1-δ))) / (Nμ(1-δ) - λ_A)

Critical Condition Analysis

There exists a critical interference factor δ* where:

Wq_A^pri(δ*) = Wq_A^iso

i.e., ErlangC(N, λ_A/(μ(1-δ*))) / (Nμ(1-δ*) - λ_A)
    = ErlangC(k, λ_A/μ) / (kμ - λ_A)

When δ < δ*: Priority Pareto-dominates CPUMask
When δ > δ*: True Tradeoff exists (neither dominates)

Typical δ* values:
  Small system (N=2-4): δ* ≈ 10-20%
  Medium system (N=8):  δ* ≈ 15-25%
  Large system (N=16+): δ* ≈ 20-35%

Mitigation Strategies

Hardware: Cache Partitioning

Intel CAT, ARM MPAM — divide L3 into exclusive partitions per task

Hardware: Cache Coloring

Partition physical cache by "color", bind tasks to specific colors

Software: CPU Affinity

Bind A to specific cores to reduce cross-core cache migration

Software: Preemption-Aware Scheduling

When A is preempted, prefer scheduling to same core to maximize cache reuse

Decision Framework

Step 1: Measure δ for your workload
  Method: Run A isolated → T_iso
         Run A shared with B → T_share
         δ = (T_share - T_iso) / T_iso

Step 2: Compare with δ*
  If δ < δ*: Choose Priority (Pareto-dominates)
  If δ > δ*: Evaluate what's more important

Step 3: Decide based on requirements
  A needs latency determinism? → CPUMask (k≥1) + cache partitioning
  Throughput > determinism? → Priority + mitigation
  Extreme resource constraints? → Pure Priority (k=0)

Recommended: k=1 (minimum safety net) + Priority
             Use minimal CPUMask for engineering certainty

Key Insights

  • 1. Cache interference is a real, measurable performance loss — δ is not theoretical
  • 2. δ changes the Pareto frontier — when δ is large, CPUMask and Priority become a true tradeoff
  • 3. δ can be mitigated but not eliminated — hardware (CAT) and software (affinity) solutions exist
  • 4. Measurement is key — use real data to drive decisions, not theoretical推导
  • 5. k=1 is the recommended starting point for practical systems
